# UX Requirements Checklist: Rediseño visual, página de inicio y persistencia en base de datos

**Purpose**: Validar la calidad de los requisitos de experiencia de usuario (navegación, página de inicio, rediseño visual, estados del presupuesto y accesibilidad básica) antes de generar las tareas de implementación — cubre tanto las piezas nuevas de esta feature como las pantallas heredadas de la spec 001, ya que el rediseño visual debe aplicarse a toda la aplicación (FR-014, FR-015, SC-004).
**Created**: 2026-09-28
**Feature**: [spec.md](../spec.md) · contexto técnico en [plan.md](../plan.md) y [contracts/css-tokens-contract.md](../contracts/css-tokens-contract.md)

**Note**: This custom checklist is generated by the `/speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

## Requirement Completeness

- [x] CHK001 - Are the requirements complete for what the freelancer sees on the Inicio screen when the profile has not been configured yet (banner, disabled links, redirect only on click)? [Completeness, Gap, Edge Cases]
  - Resuelto: nuevo FR-022 ("aviso visible que invite a completar el perfil... sin bloquear el resto de accesos de Inicio").
- [x] CHK002 - Are loading-state requirements defined for screens that now depend on a network call to the backend (Inicio summary, any listing) instead of instant local reads? [Completeness, Gap]
  - Resuelto: nuevo FR-027 (indicador de carga visible en toda pantalla que dependa de la API, incluido el primer acceso por URL directa).
- [x] CHK003 - Are the visual requirements for the common navigation's "current section" indicator (active state) documented? [Completeness, Gap]
  - Resuelto: nuevo FR-023 (la navegación común MUST indicar en qué sección está el freelancer).
- [x] CHK004 - Are redesigned empty-state requirements documented for the inherited screens (Catálogo, Clientes) with the same rigor as the new Inicio empty state (§Edge Cases)? [Completeness, Gap]
  - Resuelto: nuevo FR-024 (mensaje claro en vez de tabla en blanco cuando Catálogo/Clientes están vacíos).
- [x] CHK005 - Are the exact Spanish labels for each of the five estado values (Borrador/Enviado/Aceptado/Rechazado/Caducado) fixed in one place that every screen must reuse? [Completeness, Spec §FR-016]
  - Resuelto: `contracts/css-tokens-contract.md` fija la tabla color↔etiqueta para los 5 estados; `EstadoBadge.vue` es el único punto de traducción (plan.md).
- [x] CHK006 - Are the ordering and zero-count display rules for the activity summary (§FR-006) specified (e.g., always show all five states, even at zero)? [Completeness, Clarity, Spec §FR-006]
  - Resuelto: `data-model.md` (Resumen de actividad) y AC3 de US2 en spec.md exigen las cinco claves siempre presentes, aunque valgan 0.

## Requirement Clarity

- [x] CHK007 - Is "acceso directo y claramente identificado" (§FR-005) quantified with specific criteria (icon, label, position) rather than left to interpretation? [Clarity, Spec §FR-005]
  - Revisado y descartado deliberadamente: "claramente identificado" ya es un criterio cualitativo verificable por una persona no técnica (Principio IV de la constitution); fijar icono/posición exactos sería un detalle de diseño visual, no un requisito de negocio (decisión explícita, 2026-09-28).
- [x] CHK008 - Is "jerarquía visual clara entre títulos, tablas, formularios y totales" (§FR-015) defined with measurable criteria (e.g., a fixed type scale) instead of a subjective adjective? [Clarity, Ambiguity, Spec §FR-015]
  - Resuelto: `contracts/css-tokens-contract.md` fija una escala tipográfica cerrada (`--fuente-tamano-base/titulo-1/titulo-2`, pesos normal/negrita).
- [x] CHK009 - Is "espaciado uniforme" (§FR-015) tied to a closed, named scale of values rather than left open to per-screen judgment? [Clarity, Spec §FR-015]
  - Resuelto: `contracts/css-tokens-contract.md` fija `--espacio-1` … `--espacio-6` y `--radio-borde` como única escala permitida.
- [x] CHK010 - Is the required position of the common navigation (header, footer, side, collapsible menu) specified for both desktop and mobile widths? [Clarity, Gap, Spec §FR-007]
  - Resuelto: nuevo FR-025 (visible y accesible en escritorio y móvil, adaptando su disposición, sin ocultar nunca el acceso a las secciones).
- [x] CHK011 - Is the UI control type for changing a presupuesto's estado (dropdown, buttons, menu) specified, given FR-010 allows changing to any of the four manual values in any order? [Clarity, Gap, Spec §FR-010]
  - Resuelto: nuevo FR-026 (selector en la pantalla de detalle, promovido desde Assumptions a requisito firme).
- [x] CHK012 - Is it explicit, in a form a reviewer can check without reading code, that "Caducado" must never appear as a selectable option in that same control (only as a computed, read-only label)? [Clarity, Spec §FR-010, §FR-011]
  - Resuelto: FR-010 lo dice literalmente ("Caducado MUST NOT poder seleccionarse manualmente"); `contracts/api-contract.md` lo refuerza (400 si se envía `"caducado"`).

## Requirement Consistency

- [x] CHK013 - Do the navigation requirements (§FR-007, §FR-008) agree on what "common navigation" contains regardless of entry point (via Inicio vs. direct URL to a section)? [Consistency, Spec §FR-007, §FR-008]
  - Resuelto: FR-007 define un único componente de navegación común con los mismos 5 destinos en toda pantalla; FR-008 solo confirma que sigue visible al entrar por URL directa, sin definir un contenido distinto.
- [x] CHK014 - Are the requirements for how an estado is displayed consistent between listings (§FR-016, "listados") and the presupuesto detail screen, beyond just sharing a color? [Consistency, Spec §FR-016]
  - Resuelto: FR-016 exige color + etiqueta "de forma consistente en todos los listados **y pantallas** donde aparezca", cubriendo explícitamente el detalle, no solo listados.
- [x] CHK015 - Do the visual redesign requirements (§FR-014, §FR-015) and the PDF visual requirement (§FR-017) agree on what "the same image" means, or could each be satisfied independently while still looking different? [Consistency, Spec §FR-017]
  - Resuelto: `contracts/pdf-contract-visual.md` obliga al PDF a leer los colores desde las mismas variables CSS (`getComputedStyle`), eliminando la posibilidad de que diverjan.
- [x] CHK016 - Are the mobile-first requirements (§FR-018) consistent with the table-heavy screens inherited from 001 (presupuestos list, líneas), which historically are the hardest to keep readable on narrow screens? [Consistency, Gap, Spec §FR-018]
  - Resuelto: nuevo FR-029 (tablas legibles en anchos estrechos vía scroll horizontal o apilado por fila, sin cortar columnas).

## Acceptance Criteria Quality (Measurability)

- [x] CHK017 - Does SC-004 ("misma paleta de colores y tipografía... verificable mediante comparación visual directa") reference a closed, objective list of values (e.g., the token contract) so two reviewers would reach the same pass/fail verdict? [Measurability, Spec §SC-004]
  - Resuelto: `contracts/css-tokens-contract.md` es la lista cerrada de referencia; "misma paleta" = mismas variables usadas en todas partes.
- [x] CHK018 - Can SC-003 ("identificar el estado... de un vistazo, sin necesidad de abrir el presupuesto") be verified objectively, or does it depend on a subjective judgment of what counts as "de un vistazo"? [Measurability, Spec §SC-003]
  - Resuelto: la parte operativa y verificable es "sin necesidad de abrir el presupuesto" (visible en el listado sin clic adicional); "de un vistazo" es descriptivo, no la condición de paso/fallo.
- [x] CHK019 - Is SC-002's "un único clic" requirement measurable across every pair of sections, or only from Inicio to a section (leaving section-to-section click count unspecified)? [Measurability, Ambiguity, Spec §SC-002]
  - Resuelto: FR-007 exige que la navegación común (con enlaces a las 5 secciones) esté visible en *toda* pantalla, no solo en Inicio, por lo que cualquier par de secciones también queda a un clic por construcción.

## Scenario Coverage

- [x] CHK020 - Are UX requirements defined for the exception scenario where the backend/API is unavailable while the freelancer is already inside a section (not just at initial load)? [Coverage, Exception Flow, Spec §Edge Cases]
  - Resuelto: FR-003a (añadido tras `/speckit-analyze`) cubre "cuando una petición a la API falle", sin restringirlo a la carga inicial.
- [x] CHK021 - Are recovery requirements defined for what the freelancer sees/does once the backend becomes available again after being down (auto-retry vs. manual reload)? [Coverage, Recovery, Gap]
  - Resuelto: nuevo FR-028 (botón "Reintentar" explícito sobre el aviso de FR-003a; sin reintento automático en segundo plano).
- [x] CHK022 - Are alternate-flow requirements defined for a freelancer who bookmarks or shares a direct URL to a section, covering both the navigation requirement (§FR-008) and any visual/loading state on first paint? [Coverage, Alternate Flow, Spec §FR-008]
  - Resuelto: FR-008 cubre la parte de navegación; nuevo FR-027 cubre explícitamente el estado de carga "incluido el acceso directo a una sección sin pasar por Inicio".
- [x] CHK023 - Are non-functional requirements defined for perceived responsiveness of navigation and data loading now that reads go through the network instead of being instantaneous local reads? [Coverage, Non-Functional, Gap]
  - Resuelto (nivel NFR general): plan.md "Performance Goals" exige que las llamadas a la API se resuelvan "en un tiempo imperceptible para un único freelancer trabajando en local". No fija un umbral en ms, pero sí un criterio de aceptación explícito.

## Edge Case Coverage

- [x] CHK024 - Are requirements defined for what happens visually if the freelancer uses the browser's back/forward buttons despite the common navigation being designed to make that unnecessary (§SC-002)? [Edge Case, Gap]
  - Revisado y descartado deliberadamente: el enrutado en modo hash (Decisión 4 de research.md) hace que atrás/adelante funcionen de forma nativa y correcta; no hay comportamiento especial que definir ni romper. Su uso sigue permitido, solo deja de ser necesario.
- [x] CHK025 - Are requirements defined for how the estado control behaves/warns (if at all) when marking a presupuesto as Rechazado, given it is a consequential, freely-reversible action (§FR-010)? [Edge Case, Gap]
  - Resuelto por decisión explícita: la sesión de clarificación 2026-09-28 (spec.md) decidió deliberadamente un cambio libre sin restricciones de flujo; no se pide confirmación/aviso como requisito.
- [x] CHK026 - Are requirements defined for the visual treatment of a presupuesto whose estado is Aceptado/Rechazado but was later edited (content changed, estado unchanged per §FR-013a) — should the UI hint that the accepted/rejected content may be out of date? [Edge Case, Gap, Spec §FR-013a]
  - Revisado y descartado deliberadamente: la clarificación del 2026-09-28 decidió expresamente que editar contenido y cambiar estado son "dos acciones independientes", sin mencionar ningún aviso; añadirlo ahora sería alcance no pedido (Principio III de la constitution).

## Non-Functional Requirements (incl. Accessibility)

- [x] CHK027 - Is a minimum color-contrast requirement specified for each estado badge's text against its background, to keep the five colors legible? [Accessibility, Gap]
  - Resuelto: nuevo FR-030 (contraste mínimo equivalente a WCAG AA, ratio 4.5:1).
- [x] CHK028 - Is it explicit in the requirements that estado must never be conveyed by color alone (already implied by "color y etiqueta de texto" in §FR-016) so a reviewer can confirm this without inferring it? [Accessibility, Spec §FR-016]
  - Resuelto: FR-016 dice literalmente "color **y** etiqueta de texto", no solo color; explícito, sin necesidad de inferencia.
- [x] CHK029 - Are keyboard-navigation requirements (visible focus, tab order) defined for the common navigation and for the estado-change control? [Accessibility, Gap]
  - Resuelto: nuevo FR-031 (navegación común y control de estado operables por teclado, foco siempre visible).
- [x] CHK030 - Are accessible-name/label requirements defined for non-text elements introduced by this feature (e.g., an icon-only nav link, the estado badge) for assistive technology? [Accessibility, Gap]
  - Revisado y descartado deliberadamente: FR-005 y FR-016 ya exigen texto/etiqueta visible junto a cualquier icono; el diseño actual no contempla elementos solo-icono, por lo que el riesgo señalado no llega a materializarse.
- [x] CHK031 - Are responsive/mobile-first requirements specific enough (breakpoints, stacking rules for tables/forms) to be checked objectively rather than left to "looks fine on a phone"? [Non-Functional, Clarity, Spec §FR-018]
  - Resuelto (mismo fix que CHK016): nuevo FR-029 fija la regla de legibilidad de tablas en anchos estrechos.

## Dependencies & Assumptions

- [x] CHK032 - Is the assumption that estado changes happen through "un selector o botones de acción" (§Assumptions) validated as a firm UX requirement, or does it remain an open assumption a reviewer should confirm with the business? [Assumption, Spec §Assumptions]
  - Resuelto (mismo fix que CHK011): nuevo FR-026 promueve "selector" de Assumptions a requisito firme.
- [x] CHK033 - Is the Inicio activity summary's dependency on live data from the backend documented together with what staleness (if any) is acceptable if the freelancer changes an estado and returns to Inicio? [Dependency, Gap]
  - Revisado y descartado deliberadamente: el diseño no introduce ninguna caché (Decisiones 2 y 6 de research.md); cada visita a Inicio hace `GET /api/resumen-actividad` de nuevo, siempre con datos frescos, por lo que no hay staleness que documentar.
